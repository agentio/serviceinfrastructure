# Quickstart Details

## The Boba Dojo Stores API

The Boba Dojo Stores API is a sample that demonstrates the creation and management of a Protocol Buffer-based API.

If it existed, the Boba Dojo would be your favorite place to hang out and enjoy the finest bubble teas and related treats. But for now, it's purely fictional, and (fictionally) it's the largest chain of bubble tea shops in the United States. As the large retail business that it is, it needs APIs!

We've sketched a family of Boba Dojo APIs in the [bobadojo/apis](https://github.com/bobadojo/apis) repo, and the Boba Dojo Store Finder API is described in [bobadojo/stores/v1/stores.proto](https://github.com/bobadojo/apis/blob/main/bobadojo/stores/v1/stores.proto).

### stores.proto (excerpted)

```
// Get stores and related information.
service Stores {
  // List all stores.
  rpc ListStores(ListStoresRequest) returns (ListStoresResponse) {
    // Client example (Assuming your service is hosted at the given 'DOMAIN_NAME'):
    //   curl http://DOMAIN_NAME/v1/stores
    option (google.api.http) = { get: "/v1/stores" };
  }
  // Returns a list of all stores in a specified region.
  rpc FindStores(FindStoresRequest) returns (FindStoresResponse) {
    // Define HTTP mapping.
    // Client example (Assuming your service is hosted at the given 'DOMAIN_NAME'):
    //   curl http://DOMAIN_NAME/v1/stores:find
    option (google.api.http) = { get: "/v1/stores:find" };
  }
  // Returns a specific store.
  rpc GetStore(GetStoreRequest) returns (Store) {
    // Client example - returns the first store:
    //   curl http://DOMAIN_NAME/v1/stores/1
    option (google.api.http) = { get: "/v1/{name=stores/*}" };
    option (google.api.method_signature) = "name";
  }
}
```

## The sample Stores server

We've put a sample implementation of the Stores API in [bobadojo/stores-server](https://github.com/bobadojo/stores-server). To have a nice large data set, we use [post office locations](https://github.com/bobadojo/stores-server/blob/main/data/stores.csv) that we pulled from Open Street Map (who doesn't want bubble tea with their bubble wrap?).

The [bobadojo/stores-server](https://github.com/bobadojo/stores-server) repo includes a [Dockerfile](https://github.com/bobadojo/stores-server/blob/main/Dockerfile) and a [GitHub Action](https://github.com/bobadojo/stores-server/blob/main/.github/workflows/docker-publish.yml) that produces [container builds](https://github.com/bobadojo/stores-server/pkgs/container/stores-server) of the server for both `linux/amd64` and `linux/arm64`.

## Running the Stores server on Kubernetes

The script generated by `q demo` deploys the Stores server to Cloud Run, but we can also easily deploy it to a Kubernetes cluster.

We've deployed the Stores server to Kubernetes using the YAML below. It has three main parts: an ingress, a service, and a deployment.

### ingress.yaml

Here's the ingress. Note that we're using [microk8s](https://microk8s.io/) and the [NGINX Ingress Addon](https://microk8s.io/docs/addon-ingress), which we need to configure specially for gRPC. We're also using the [Cert Manager Addon](https://microk8s.io/docs/addon-cert-manager) to generate SSL certs from [Lets Encrypt](https://letsencrypt.org/), and we're serving the API on two domains:
- stores.timbx.me, domain that we personally control and manage
- stores.endpoints.bobadojo.cloud.goog, a domain that Google manages for us using information that we put in our service config.

```
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: stores
  namespace: bobadojo
  annotations:
    nginx.ingress.kubernetes.io/backend-protocol: "GRPC"
    cert-manager.io/cluster-issuer: letsencrypt
spec:
  tls:
  - hosts:
      - stores.timbx.me
      - stores.endpoints.bobadojo.cloud.goog
    secretName: stores-tls
  rules:
  - host: stores.timbx.me
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: stores
            port:
              number: 80
  - host: stores.endpoints.bobadojo.cloud.goog
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: stores
            port:
              number: 80
```

### service.yaml

The ingress is exposing a service. Here's the service definition:

```
apiVersion: v1
kind: Service
metadata:
  labels:
    run: stores
  name: stores
  namespace: bobadojo
spec:
  ports:
  - port: 80
    protocol: TCP
    targetPort: 8081
  selector:
    run: stores
```

### deployment.yaml

Finally, here's the most interesting part, the deployment:

```
apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    run: stores
  name: stores
  namespace: bobadojo
spec:
  selector:
    matchLabels:
      run: stores
  template:
    metadata:
      labels:
        run: stores
    spec:
      volumes:
        - name: service-account-creds
          secret:
            secretName: service-account-creds
      containers:
      - name: stores
        image: ghcr.io/bobadojo/stores-server:latest
      - name: esp
        image: gcr.io/endpoints-release/endpoints-runtime:2
        args: [
          "--listener_port=8081",
          "--backend=grpc://127.0.0.1:8080",
          "--service=stores.endpoints.bobadojo.cloud.goog",
          "--rollout_strategy=managed",
          "--non_gcp",
          "--service_account_key=/etc/esp/creds/service-account-creds.json"
        ]
        ports:
          - containerPort: 8081
        volumeMounts:
          - mountPath: /etc/esp/creds
            name: service-account-creds
            readOnly: true
      restartPolicy: Always
      nodeSelector:
        kubernetes.io/arch: amd64
```

Note that there are two containers in the deployment. One is our gRPC server, which is serving on port 8080. The other is ESPv2, one of the Extensible Service Proxies, and you can see the set of options that we're specifying, which include the name of the service and the path to a file that contains credentials for the service account that will be used to make the calls to Service Control.

A Kubernetes secret provides the service account credentials. We create that with the following `kubectl` command, where `service-account-creds.json` is a local file that contains a service account key that we downloaded from the Google Cloud Console.
```
kubectl create secret generic --from-file service-account-creds.json -n bobadojo service-account-creds
```

If you read through [SETUP.sh](/docs/quickstart/files#setupsh) in the `q demo` output, you know that this service account needs to have these two roles:
- `roles/servicemanagement.serviceController`
- `roles/cloudtrace.agent`

## A Stores test client

A simple Stores client is in [stores-server/cmd/stores-client](https://github.com/bobadojo/stores-server/blob/main/cmd/stores-client/main.go). It calls `FindStores` with a random region and then calls `GetStore` for each of the stores that was returned. This usually results in 30-40 calls to the Stores API. It can be run locally or as a Kubernetes cron job. The configuration below runs the test client every five minutes:

### client.yaml

```
apiVersion: batch/v1
kind: CronJob
metadata:
  name: stores-client
  namespace: bobadojo
spec:
  schedule: "*/5 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: stores-client
            image: ghcr.io/bobadojo/stores-client:latest
            imagePullPolicy: IfNotPresent
            command:
            - /usr/local/bin/stores-client
            - -addr
            - stores.timbx.me:443
            - -api-key
            - $(key)
            envFrom:
            - secretRef:
                name: apikey
          restartPolicy: OnFailure
          nodeSelector:
            kubernetes.io/arch: arm64
```

The client uses an API key stored in a secret. You can create the secret with the following YAML (after you replace `YOURAPIKEYGOESHERE` with your API key):

### secret.yaml

```
apiVersion: v1
kind: Secret
metadata:
  name: apikey
  namespace: bobadojo
type: Opaque
stringData:
  key: YOURAPIKEYGOESHERE
```
